# RMCP-F-0069 — current serving-instance epoch overwritten by historical manager fields

Observed in source after #796 (v0.1.76), not a proven live exploit. The existing `runtime_status` first added `serving_instance_epoch` and `serving_instance_epoch_authenticated=false`, then sequentially merged self-update, Fabric bootstrap and Fabric update status dictionaries with `result.update(state)`. If a status producer returned colliding fields, a stale or foreign epoch, or an optimistic authenticated=true, that could survive in the reply. Similar confusion exists today between the separate primary/lab 0.1.38 services and lab interactive CLI 0.1.3. The source code bug did not cause or prove those existing observations, but could undermine their future correlation feature.

Mitigation in #797 v0.1.77: bind the epoch supplied by the actual `build_mcp` serving instance **only in the final `fail_closed_runtime_provenance` normalizer**, overriding all merged manager fields. Only a 32-character lowercase hex local epoch may be supplied. No epoch means null and unauthenticated, not a guessed PID/host. Version equality, local module-roster observations and a server epoch remain untrusted hints, not an independently signed wheel, host, original-client route, six-role process map or complete ACK.

Regressions: `tests/unit/test_build_identity.py` foreign epoch, manager boolean spoof, missing and malformed local epoch, unchanged fail-closed update readiness; full normal exact-head CI of PR #797 required before source merge. Central production 0.1.38 unaffected. Correct-host old wheel/RECORD plus physically distinct A6/A7/ACK remains a separate operational gate under #669/Fabric #924.
